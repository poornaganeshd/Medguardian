# Drug Interaction Engine

**Dataset:** [`backend/src/data/drugInteractions.json`](../backend/src/data/drugInteractions.json)
**Engine:** [`backend/src/services/drugInteractionService.js`](../backend/src/services/drugInteractionService.js)
**Normaliser:** [`backend/src/utils/drugNameNormalizer.js`](../backend/src/utils/drugNameNormalizer.js)
**Tests:** 25 engine tests + 14 normaliser tests + 8 integration tests

---

## 1. The requirement, and why it shapes everything

The project specification is explicit:

> Use a validated/structured dataset, not an LLM, to determine drug
> interactions. The interaction engine must be deterministic and dataset/rule
> based. **Do NOT allow an AI model to invent drug interactions.**

This is the right constraint. A language model asked "do warfarin and aspirin
interact?" will produce a fluent, plausible answer — and will produce an
equally fluent, equally plausible answer for two drugs that have no documented
interaction at all, or invent a mechanism that does not exist. For a patient
deciding whether to take a tablet, a confident wrong answer is worse than no
answer.

So the engine does exactly one thing: **it looks the pair up in a file.**

| Property | Guarantee |
|----------|-----------|
| Deterministic | The same two medicines always produce the same result |
| Grounded | Severity, description, mechanism and precautions are copied **verbatim** from the dataset |
| Honest about absence | A pair not in the dataset returns "no known interaction *in this dataset*", never a guess |
| No model | `llmInvolved: false` is returned on every response and asserted by a test |

## 2. Dataset

### Provenance

The bundled dataset is **clearly and repeatedly marked as demonstration data**:

```json
{
  "datasetName": "MedGuardian Demo Drug Interaction Dataset",
  "version": "1.0.0",
  "isDemoData": true,
  "demoDataNotice": "DEMO DATA FOR ACADEMIC DEMONSTRATION ONLY. This is a small,
    hand-curated subset of well-documented drug-drug interactions… It is NOT a
    complete or clinically validated interaction database and MUST NOT be used
    to make treatment decisions…",
  "sourceNotes": "Interaction pairs and severity bands were compiled from widely
    published, non-proprietary drug interaction summaries… No interaction in this
    file was generated by a language model."
}
```

The notice travels with **every API response** and is rendered as a prominent
banner on the Drug Interactions screen. A patient can never see a result
without also seeing what produced it.

### Contents

| Item | Count |
|------|-------|
| Interaction pairs | 30 |
| Duplicate-therapy groups | 5 |
| Distinct substances | 47 |

### Record shape

```json
{
  "id": "DDI-001",
  "drugA": "warfarin",
  "drugB": "aspirin",
  "severity": "major",
  "description": "Both medicines reduce the blood's ability to clot. Taken
    together they substantially increase the risk of bleeding, including
    stomach bleeding.",
  "mechanism": "Additive anticoagulant and antiplatelet effect; aspirin also
    irritates the stomach lining.",
  "precautions": [
    "Do not start or stop either medicine without medical advice.",
    "Watch for unusual bruising, nosebleeds, black stools or blood in urine.",
    "Report any of these signs to your doctor immediately."
  ]
}
```

### Severity scale

| Severity | Meaning |
|----------|---------|
| `major` | Clinically significant. Usually avoided, or requires close medical supervision |
| `moderate` | May require dose adjustment, extra monitoring, or spacing the doses apart |
| `minor` | Usually manageable. Worth being aware of, rarely requires a change |

### Duplicate therapy groups

Beyond pairwise interactions, the dataset defines therapeutic groups where
taking two members together is itself the problem:

| Group | Members | Severity |
|-------|---------|----------|
| NSAIDs | ibuprofen, naproxen, diclofenac, aspirin, indomethacin, ketorolac | moderate |
| Statins | atorvastatin, simvastatin, rosuvastatin, pravastatin | major |
| Proton pump inhibitors | omeprazole, pantoprazole, esomeprazole, lansoprazole, rabeprazole | minor |
| SSRIs | sertraline, fluoxetine, citalopram, escitalopram, paroxetine | major |
| Paracetamol-containing | paracetamol | major |

The paracetamol group exists because paracetamol hides inside dozens of
combination cold and pain products. Two such products can quietly exceed the
safe daily limit, and that is exactly the kind of thing a patient cannot be
expected to spot on a label.

### Replacing it with a real dataset

The record shape deliberately mirrors what a licensed source provides. To swap
in DrugBank, RxNorm + the NLM DDI set, or a national formulary feed, transform
that source into this JSON shape and set `isDemoData: false`. No engine code
changes — the index builds from whatever the file contains.

## 3. Name normalisation

The hard part of interaction checking is not the lookup, it is deciding that
"Tab. Ecosprin 75mg", "Ecosprin", "ASPIRIN" and "acetylsalicylic acid" are all
the same substance.

[`drugNameNormalizer.js`](../backend/src/utils/drugNameNormalizer.js) does this
with rules only — no fuzzy matching, no model, no network call.

### Pipeline

| Stage | Action | Example |
|-------|--------|---------|
| 1 | Lower-case, strip accents and symbols | `Amoxicilliné®` → `amoxicilline` |
| 2 | Drop parenthetical notes | `Warfarin (blood thinner)` → `warfarin` |
| 3 | Strip dosage strengths | `Metformin 500 mg` → `metformin` |
| 4 | Split combinations on `+` and `/` | `Amoxicillin + Clavulanic Acid` → two parts |
| 5 | Remove pack/form noise | `tab`, `cap`, `syrup`, `sr`, `xr`, `film coated`, … |
| 6 | Map brand → generic | `ecosprin` → `aspirin`, `dolo` → `paracetamol` |
| 7 | Sort and rejoin combinations | order-independent key |

### Results

| Input | Normalised |
|-------|-----------|
| `Metformin` | `metformin` |
| `METFORMIN 500 MG SR TABLET` | `metformin` |
| `Tab. Ecosprin 75mg` | `aspirin` |
| `Dolo 650` | `paracetamol` |
| `Acetaminophen` | `paracetamol` |
| `Coumadin` | `warfarin` |
| `Amoxicillin + Clavulanic Acid` | `amoxicillin+clavulanicacid` |
| `Clavulanic Acid + Amoxicillin` | `amoxicillin+clavulanicacid` |
| `Tablet` | `` (empty — no substance) |

The last two matter. Combination keys are **order-independent**, so the same
product written either way round matches the same records. And a string with no
substance in it produces an empty key rather than a spurious match.

The normalised name is stored on every medicine as `normalizedName` and kept in
sync by a Mongoose `pre('validate')` hook, so changing a medicine's generic
name re-normalises it automatically.

## 4. Matching

### Index

Built once at module load. Each record is keyed on an order-independent pair
key, making every lookup O(1):

```js
function pairKey(a, b) {
  return a < b ? `${a}|${b}` : `${b}|${a}`;
}
```

### Algorithm

```
for each unordered pair of medicines (i, j):
    for each substance a in medicine i:
        for each substance b in medicine j:
            record = index.get(pairKey(a, b))
            if record exists and not already reported for this medicine pair:
                emit finding, copying every field verbatim
```

The nested substance loops are what make combination products work: a patient
taking "Ibuprofen + Paracetamol" alongside warfarin gets **two** findings — one
for the ibuprofen (major) and one for the paracetamol (minor) — because both
substances are checked independently.

### Guarantees

- A medicine is never paired with itself, and two medicines resolving to the
  same substance produce no finding.
- Findings are deduplicated per (medicine pair, dataset record).
- Results are sorted major → moderate → minor.
- Medicine ids are carried through, so the UI can link each finding back to the
  medicine in the patient's list.

### Response

```json
{
  "findings": [ /* … */ ],
  "duplicateTherapy": [ /* … */ ],
  "summary": {
    "medicinesChecked": 3,
    "checkedPairs": 3,
    "total": 2,
    "major": 1, "moderate": 0, "minor": 1,
    "duplicateTherapyGroups": 0,
    "highestSeverity": "major"
  },
  "dataset": { "isDemoData": true, "demoDataNotice": "…", "recordCount": 30 },
  "disclaimer": "This check is a lookup against a bundled demo dataset and is
    not a substitute for professional advice. A result of \"no interactions
    found\" only means this dataset holds no record for these medicines…",
  "method": "deterministic-dataset-lookup"
}
```

Note the disclaimer's second sentence. "No interactions found" is a statement
about the dataset, not about pharmacology, and the wording says so.

## 5. Endpoints

| Method | Path | Purpose |
|--------|------|---------|
| `GET` | `/api/interactions/my-medicines` | Check every active medicine against each other |
| `POST` | `/api/interactions/check` | Check typed names, optionally combined with the patient's list |
| `GET` | `/api/interactions/dataset` | Dataset provenance and known substances |

`POST /check` is what a patient uses before buying something over the counter:
type "ibuprofen", leave *also check against my current medicines* ticked, and
find out that it clashes with the warfarin they already take.

## 6. Where the assistant defers

The medicine information assistant (`/api/assistant/medicine-info`) explicitly
**refuses** interaction questions and redirects to this engine:

```js
{
  id: 'INTERACTION',
  pattern: /\b(interact|interaction|safe to (take|combine|mix)|…)\b/i,
  message: 'Interaction questions are answered by the Drug Interactions screen,
    which checks your medicines against a fixed, reviewed dataset rather than
    describing them in prose…',
  redirectTo: 'drug_interaction_checker'
}
```

This is the boundary that keeps the "no LLM invents interactions" requirement
intact end to end. A retrieval assistant could in principle stitch together a
plausible-sounding interaction claim from two unrelated knowledge-base entries;
refusing the question category outright removes that possibility.

## 7. What the tests enforce

```bash
cd backend
npx jest tests/unit/drugInteractionService tests/unit/drugNameNormalizer
```

**Dataset integrity** — demo flag present, notice mentions incompleteness,
source notes state no LLM generation, ids unique, every record complete, no drug
paired with itself.

**Matching** — known pairs found; brand names resolved; order-independent;
combination products decomposed; longer lists check every pair; results sorted
by severity; medicine ids preserved.

**No false positives** — unknown pairs return nothing; a medicine is never
paired with itself; empty and unusable input handled; no duplicate findings.

**Determinism and grounding** — identical input gives byte-identical output;
`method` is `deterministic-dataset-lookup`; every field matches the dataset
record exactly; the demo notice and disclaimer are always attached.

**Duplicate therapy** — two NSAIDs flagged; two statins flagged as major;
hidden paracetamol in two products flagged with the 4 g warning; a single group
member never flagged.

## 8. Limitations

Stated plainly, because a project of this kind should be honest about what it
does not do:

- **The dataset is small.** 30 pairs against a real interaction database's tens
  of thousands. It demonstrates the mechanism, not clinical coverage.
- **Only pairwise.** Three-drug interactions that emerge only in combination
  are not modelled.
- **No patient context.** Real interaction significance depends on dose, renal
  and hepatic function, age and indication. None of that is considered.
- **No food, alcohol or supplement coverage** beyond the two illustrative
  entries (metronidazole + alcohol, cetirizine + alcohol).
- **Normalisation is finite.** The brand map covers common Indian and
  international brands; an unlisted brand normalises to itself and simply will
  not match. This fails safe — it produces a missed finding, never a fabricated
  one — but a patient should still enter the generic name where they know it,
  and the medicine form's hint says so.

Every one of these is a reason the disclaimer tells the patient to confirm with
a pharmacist.
